We are mounting the portfolio html file and the default config using config maps.
There were issues with mounting the file using its absolute file path. it wasnt being recognised
leaving the /usr/share/nginx/html directory empty in the pod, causing a 403 forbidden error.

The config map loads in the contents of my portfolio file directly. So rather than specifying a file path,
the deployment just has to look inside the configmap for my portfolio. Similarly for the default config file.

I must update the configmaps whenever I update the portfolio. Do this with:

$ kubectl create configmap config --from-file=Frontend/default.conf --dry-run=client -o yaml > ConfigMaps/frontend-default-config.yml

$ kubectl create configmap webpage --from-file=Frontend/index.html --dry-run=client -o yaml > ConfigMaps/frontend-index-config.yml

18/06/2026 Frontend talks to backend
We now have the front end talking to the backend
The frontend is exposed outside the cluster via a NodePort service. We then run $ minikube service <frontend_service_name> to create a port forwarding
to the front end.
The backend is exposed within the cluster via ClusterIP. 
The frontend is connected to the backend using a proxy. when the "/api" url is called from the front end, this is forwarded to the backend service on port 8000,
where the backend pod listens. We can see this configured in Frontend/default.conf. Then in the index.html, clicking the "qualifications"
button is coded to trigger the url "/api/qualifications" which is forwarded to http://<backend_service>:8000/qualifications. 
This triggers the get request "qualifications" which (currently) returns some data about my grades

## Helpful troubleshooting tips
use (for e.g) kubectl port-forward svc/backend-service 9000:8000 to see the backend in your browser on the fly
use kubectl exec -it <nginx pod> and look in the relevant directories to check things are mounted correctly

## Network policies
Added network policies to enforce connections and port numebrs between pods
Important - I added a policy which default-denies all ingress/egress on all pods, then i made policies to make exceptions
A lot of k8s functionality relies of networking between pods. A good example of the core-dns pod. The pods need this to be able to translate service names
into the IPs. So this was causing an issue before i created a policy to allow connections to the core-dns pod. Be careful in the future for more like this.

I had to restart the cluster with a CNI for the network policies to activate. The yml files were happily accepted before,
but had no effect. Use minikube start --cni=calico

## Issue when developing the front end using the ingress controller
When clicking on my "qualifications" button on my index.html, it routed me to /qualifications.html which is what I wanted. However, it was displaying
the contents of index.html. I ensured that qualifications.html existed in the container by exec-ing into the container. At this point I was confused.
It turns out that becuase I was port-forwarding via the ingress controller, rules defined in the ingress were superseding he rules defined by nginx.
The ingress is making any URL, even something like /doesnt-exist.html return /index.html. It wastemporarily resolved by portforwarding to the nginx
service rather than the ingress controller, but in the long term i need to change the ingress rules to by able to allow nginx to serve the files properly.
The ingress annotation was originally supposed to be applied only to requests which would be sent to the backend. But now that i am developing my frontend
and adding more webpages, the rule is having an unwanted impact. For example, if I request "/qualifications.html", the rule rewrites the request to"/"
and serves the homepage only.

Solution 1: Split the ingress into 2. One for the front end, and one for the backend with the specific rule enforced
Solution2: scrap the rule and instead configure the backend to consume endpoints beginning with "/api"
